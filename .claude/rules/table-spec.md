# Table-spec conventions

The table spec defines every Parquet table the tool writes: file name, source bundle section, sort key, and per column
its name, exact DuckDB type, empty-versus-NULL rule and derivation. From 2.0.0 there is one spec, `sections`, and it has no
file in the repo: it is compiled at run time from a bundle schema and, optionally, a column set, the *pairing* (with
none, the schema's default column set, generated by the default policy;
[ADR 0007](../../docs/decisions/0007-default-generated-from-bundle-schema.md), [`docs/generate.md`](../../docs/generate.md))
([ADR 0006](../../docs/decisions/0006-sections-spec-compiled-from-schemas.md), format in
[`docs/column-set-format.md`](../../docs/column-set-format.md)). `compiler.py` compiles it, `spec.py` checks it
(`check_compiled`), and `sqltemplate.render_generic` renders each table's SQL from it, with the macros in
`src/gkm_bundle_parquet/sql/_macros.sql`. The package ships no pairing: the producer publishes its own (ADR 0009).

What identifies a compiled table set is `table_spec_sha256`, of what affects the tables; `schema_set_sha256` and
`column_set_sha256` say what it came from. All three, and the compiled spec itself (`table-spec.json`), are in every set.

## Every column cites the bundle

Each column's `derivation` names the bundle JSON path(s) it comes from and the transform (cast, pointer strip,
range bound, extension pick by name, ...). A column whose value can't be traced to the bundle is not allowed (see
[ADR 0001](../../docs/decisions/0001-parquet-derived-from-bundles.md)).

## Version bump rules

What an existing pairing compiles to is judged by this table:

| Change | Rules bump |
| --- | --- |
| New table | MINOR |
| New column appended after the existing columns | MINOR |
| New accepted value in an existing column that follows from new bundle content (e.g. a new enum value) | none (record it in the changelog) |
| Rename, remove or reorder a column; change a type; change empty-versus-NULL behaviour | MAJOR |
| Change what a column means, or which rows a table holds | MAJOR |
| Remove or rename a table or file | MAJOR |
| Writer settings only (compression, row-group size, sort order) | none, but call it out in the tool changelog: it changes remote-query cost |

- **A pairing change needs no bump.** The columns follow the column set, so the producer names them and announces changes
  (ADR 0006).
- **A change to the rules bumps the rules version** (`compiler.RULES_VERSION`, written as `table_spec_version` and as
  the default policy's `policy_version`), by the table above. A change to what `generate` writes for a schema is a rules
  change. A tool bug fix that makes the output conform to the rules is a tool PATCH, not a rules change.
- **A built set doesn't depend on the rules:** it carries its compiled spec, so `verify` and `rebuild` read an older set
  with no recompile. They do need a tool that understands that spec's format.
- Rewording changes no hash: `table_spec_sha256` leaves out `description`, `transform`, `sources`, `status` and the
  `column_set` label (default or projection), so a column set equal to the default has the default's hash.
- The golden test (`tests/test_compiler.py` against `tests/fixtures/sections-golden/`) lists every accepted difference
  on ClinVar-GKM 1.1.0, and the lossless round trip must still pass on the real excerpts.

## What moves with a rules change (same PR)

- The rules version, the compiler and the spec checks, and the SQL macros they use.
- The compatibility matrix: `README.md` and the package's `version --json` data (`compat.py`).
- The changelog entry, listing every added, changed or removed column, on the pairings the suite holds.
- A note for the producers whose columns change (for ClinVar-GKM: its column reference `docs/parquet/tables.md` and the
  Ecosystem add-on page). This repo doesn't edit a producer's repo; open or request a paired PR there.
- A `verify --bundle-recompute` and `verify --roundtrip` run on a real bundle for the changed tables, with the result in
  the PR body.
